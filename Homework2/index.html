From Wallet Seed to Ethereum Address

Key derivation, cryptographic hashing and the statistical behaviour of Ethereum wallet operations.

01

Wallet pipeline

How the different cryptographic operations fit together.

Overview

An Ethereum address is obtained through a sequence of operations rather than one direct transformation. A mnemonic represents initial entropy, a seed supports reproducible key derivation, elliptic-curve multiplication provides the public key, and Keccak-256 determines the address bytes. EIP-55 then introduces a checksum in the written address.

The important distinction is that key management, public-key cryptography, hashing, encoding and error detection are separate operations. Each one solves a different problem, so none of these techniques can replace all the others.

Example BIP-44 path

m/44'/60'/0'/0/0

Here 44' identifies the BIP-44 purpose, 60' identifies Ethereum, 0' selects the first account, 0 selects the external receiving chain, and the final 0 selects its first address. The apostrophe indicates hardened derivation. Wallets can use other paths, so recovery sometimes requires choosing the same path as the original wallet.

Important distinctions

Key generation versus key derivation

Key generation begins with fresh, unpredictable randomness. In a BIP-39 wallet, entropy is generated and encoded as words. Key derivation is deterministic: the same mnemonic, passphrase and derivation path reproduce the same seed and account keys. A wallet can therefore recover many accounts without independently storing a random private key for every account.

Public-key cryptography

For secp256k1, a private key is a number d in a valid range and its public key is the elliptic-curve point Q = dG. Computing Q is practical; recovering d from Q is believed to be computationally infeasible with current classical methods. The key pair supports transaction signing and verification.

Hashing

A cryptographic hash maps inputs of different lengths to fixed-length outputs. Keccak-256 is designed for preimage and collision resistance, and small input changes generally alter many output bits. Hashing is not encryption and is not intended to be reversible.

Checksums

EIP-55 uses uppercase and lowercase hexadecimal letters to detect many accidental address-entry mistakes. It is not a digital signature and does not authenticate the owner of an address. An all-lowercase address can still be syntactically valid, but it has no mixed-case checksum information.

Encoding

Encoding changes how information is represented, not its cryptographic secrecy. BIP-39 maps bit sequences into words; Ethereum addresses are displayed as hexadecimal text prefixed by 0x. EIP-55 adds a checksum convention to that textual representation.

EIP-55 checksum and error detection

A standard externally owned Ethereum account address contains 20 bytes, shown as 40 hexadecimal characters after 0x. The checksum does not change the underlying 20-byte address: it only changes the capitalization of letters a through f.

Lowercase: 0x52908400098527886e0f7030069857d2e4169ee7
Checksummed: 0x52908400098527886E0F7030069857D2E4169EE7

Published EIP-55 example. The mixed-case representation is an encoding of the same address bytes.

Why the hash input matters

Ethereum hashes the 64-byte uncompressed public-key coordinates (x || y) without the 0x04 uncompressed-point prefix. The final 20 bytes of the Keccak-256 digest become the address. Using SHA3-256 instead, or hashing the hexadecimal text rather than the underlying bytes, produces the wrong result.

Experiment: can EIP-55 detect an address typo?

Starting with an official example, each trial changes one hexadecimal character of the 40-character address while leaving the existing capitalization unchanged. The experiment checks whether the altered text still matches its recalculated EIP-55 capitalization. This is a controlled error-detection experiment, not a test against malicious substitution.

04

Cryptographic discussion

Historical development and the reason each algorithm is needed.

Historical timeline

1977 RSA introduces a practical public-key cryptosystem, illustrating the separation of public and private keys.
2001 SHA-2, including SHA-512, is standardized by NIST (FIPS 180-2).
2012 BIP-32 describes hierarchical deterministic wallets.
2013 BIP-39 proposes mnemonic codes for deterministic wallets.
2014 BIP-44 proposes a standard multi-account derivation structure.
2015 NIST standardizes SHA-3, based on the Keccak design.
2016 EIP-55 proposes mixed-case checksum encoding for Ethereum addresses.

SHA-512 versus Keccak-256 versus SHA3-256

SHA-512 belongs to the SHA-2 family and produces a 512-bit digest. BIP-39 uses it inside HMAC-based PBKDF2, while BIP-32 uses HMAC-SHA512 to derive extended keys. Keccak is a different sponge-based hash design selected as the basis for the SHA-3 standard. Ethereum uses Keccak-256, which is not identical to standardized SHA3-256: their padding/domain-separation conventions differ, so the same input produces different digests.

The name “SHA-3” is therefore not interchangeable with “Ethereum Keccak-256” in wallet implementation.

Why the pipeline uses several algorithms

A wallet must solve several independent problems. Randomness and BIP-39 make backup and recovery manageable. BIP-32 and BIP-44 allow one seed to organize many deterministic accounts. secp256k1 links private and public keys and enables digital signatures. Keccak-256 compresses the public-key representation into an address and supports other Ethereum hashing operations. EIP-55 adds a human-oriented error-detection layer without changing the address itself.

These primitives have different mathematical guarantees. A hash cannot replace a signing key pair, a checksum cannot protect a secret, and an elliptic-curve operation does not by itself organize recoverable accounts. Combining specialized tools is therefore more practical and secure than expecting a single algorithm to perform unrelated jobs.

Interpretation of the statistical experiments

The hash-diffusion experiment should usually show a Hamming distance near half of the 256 output bits after a small change in input. The frequency experiment should show bit proportions fluctuating around 0.5, with smaller fluctuations as the sample size grows. These results illustrate randomness-like behavior, but passing simple frequency or avalanche tests is not proof of cryptographic security. Actual security depends on algorithm design, correct implementation, strong original entropy, and safe storage of recovery information.

Connection with everyday wallet software

Wallet interfaces such as MetaMask or Rabby normally show the recovery phrase during wallet creation and display an account address afterward, while keeping the intermediate seed, chain code and public-key calculations hidden. Importing the same recovery phrase with the same optional passphrase and derivation path should reproduce the same account. This page demonstrates that deterministic process without connecting to a wallet. No real wallet was accessed or tested.
